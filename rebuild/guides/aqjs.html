Learn how AQJS exposes selectors, helpers and prototype extensions—and why source inspection and runtime evidence matter more than familiar method names.

Home / Learn / AQJS

1. The right mental model

AQJS is a JavaScript module that exports a selector/helper surface and extends selected native prototypes. Those extensions can affect global objects and native behavior, so loading the library is not equivalent to importing a small isolated utility.

Important

The knowledgebase documents observed behavior, including defects. Do not silently reinterpret a method based on its name or “fix” its behavior in application code without a wrapper and a deliberate compatibility decision.

2. Start with the entry points

Consult the exact API inventory before depending on less familiar helpers.

3. Expect receiver-dependent behavior

Several methods are installed on more than one prototype. An Element, a NodeList and an Array do not necessarily share the same contract just because a method name is similar.

  • Check the receiver type and whether the method returns the receiver, a new collection, a scalar or undefined.
  • Check whether an empty collection is a no-op or throws.
  • Check whether methods mutate the DOM, mutate the receiver or mutate global prototypes.
  • Compare the source and minified distributions for each behavior you intend to rely on.

4. Known hazards worth remembering

  • isJSON() is a broad type/emptiness predicate; it does not parse or validate JSON text.
  • isNodeList() and related predicate helpers contain free-global references that can make behavior depend on ambient globals.
  • isObjectLiteral() has unsafe null/prototype edge cases and may classify instances in surprising ways.
  • Array.setItem() has a truthy-input path that is a no-op in the tested implementation.
  • Element.setAdjacent() is currently documented as a no-op returning its receiver.
Unresolved, not safe to assume

Promise resolver assimilation of Array.then() remains untested because the implementation may recursively resolve itself. Treat it as a hazardous thenable until an isolated test proves otherwise.

5. A disciplined integration workflow

  1. Identify the exact receiver type and distribution build.
  2. Read the API inventory row and closure-matrix status.
  3. Use a minimal browser fixture to test normal, empty, falsy and invalid inputs.
  4. Compare source and minified behavior for the same fixture.
  5. Wrap unstable APIs behind your own narrow, typed application interface.

Never test a potentially recursive thenable in the main page event loop. Use a disposable isolated browsing context with a parent-side timeout.

6. API evidence and next steps

  • AQJS API inventory — exported and extended methods.
  • API closure matrix — remaining contracts and verified evidence.
  • Predicate truth table — input/output edge cases.
  • Runtime validation matrix — browser evidence and coverage limits.
